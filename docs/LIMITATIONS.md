## 一、会拿到错误结果

### 匹配算法

#### 1. 匹配只看位置、尺寸、顶点数，不看形状、朝向与拓扑

**限制**：相似度由 4 项加权平均得出——位置距离、包围盒三边尺寸、包围盒体积、
顶点数（`core/matching.py: SIMILARITY_METRICS`），
**没有任何形状 / 朝向 / 法线 / 拓扑特征**。其中「体积」是包围盒三边之积
（`get_object_features`），与「尺寸」是**同一份信息的重复计分**，不是独立维度。
**影响**：**旋转 90° 的同一个模型照样满分匹配**（朝向不参与打分）；
实心块与等大小空心壳这类形状截然不同但尺寸与顶点数都接近的组合，
得分很容易超过默认阈值 0.7，挤掉真正正确的候选；
低模与高模顶点数差一个量级时「顶点数权重」也会把正确匹配拉低。
注意结果面板上的 **80% 分界线只是 UI 置信度配色阈值**，不是算法阈值
（真正的准入门槛是「相似度阈值」0.7 与「最小置信度」0.6）。
**应对**：**始终逐条复核「匹配结果」**，不要直接点「3. 复制顶点色」；
重点检查高置信度（≥80%）里是否有「尺寸相近但明显不是同一个东西」的组合。
形状差异大的场景切「自定义」，把尺寸 / 顶点数权重调低、距离权重调高，
用位置邻近性兜底。

#### 2. 匹配特征取自原始网格，不是求值后的网格

**限制**：`get_object_features` 用 `obj.data`（**原始网格**），
`vertex_count = len(mesh.vertices)` 是**修改器之前**的顶点数；
而取色阶段源侧用的是求值后网格（`core/cache.py`）——两处口径不一致。
**影响**：两个「形状完全一样、但细分等级不同」的模型
（本该是最理想的匹配对）会因顶点数差异被额外扣分，**与第 1 条叠加**。
**应对**：批量前尽量让参与匹配的模型处于**一致的细分状态**
（要么都应用修改器，要么都不加）；细分等级差异大时把「顶点数权重」调低。

#### 3. 一个源物体可以被任意多个目标物体共用，匹配不是一对一

**限制**：批量匹配对每个目标物体**独立**选出得分最高的源物体
（`core/matching.py: find_best_matches`），
**不排除已被其他目标选中的源物体**——10 个源、10 个目标完全可能全部指向同一个源。
**影响**：参考组里有一个「万能」模型（尺寸适中、位置居中、顶点数接近大多数物体）时，
大量目标会被它吸走，颜色分布被强行拉到同一个来源上。
**应对**：把多个「通用型」模型拆到不同集合分批处理，
或调高「相似度阈值」/「最小置信度」把可疑匹配挡在结果之外。

#### 4. 「最大匹配距离」比的是物体原点，不是模型体积

**限制**：距离计算使用 `obj.location`（物体**原点**的世界坐标），
而不是包围盒中心或表面最近距离（`get_object_features` 的 `'location'`），
原点差异会直接吃掉距离预算。**影响**：一批模型里有的原点在底面、
有的在中心（导出 / FBX 导入 / 手动设原点后很常见）——明明两个模型紧挨着，
却因原点相距很远被判为超过距离阈值而**根本不匹配**，
表现为「结果为空」或「明明并排却匹配不上」。
**应对**：批量前先统一原点
（`Object > Transform > Origin to Geometry`，选「几何中心」），
大场景还需相应调大「最大匹配距离」（默认 50）。

#### 5. 四个权重全部为 0 时不会报错，而是完全不匹配

**限制**：权重按**总和归一化**（`calculate_similarity_score`，
总权重 ≤ 0.001 时跳过归一化），把四个权重都设为 0 会让所有相似度恒为 0。
**影响**：手动调参时误把全部权重清零→「查找匹配」返回 0 条，且没有明确报错。
**应对**：至少保留一项权重不为 0。切换预设
（FAST / PRECISE / LOOSE / CLUSTER）会一次性覆盖全部参数，是最省事的恢复方式。

#### 6. 「低于 60% = ❌」这一档在默认参数下不会出现

**限制**：「相似度阈值」（默认 0.7）先把候选**丢弃**
（`if similarity < vc_tool.match_similarity_threshold: continue`，
见 `core/matching.py` 的 `find_best_matches` / `find_best_match_for_cluster`），
「最小置信度」（默认 0.6）只在**其后**过滤结果。
因此凡能进入结果列表的匹配天然都 ≥ 0.7，
`ui/results_panel.py` 里的 ❌ 分支（< 60%）**永不触发**。
**影响**：面板「≥80% ✅ / 60–80% ℹ️ / <60% ❌」的三档说法在实际数据上对不上
——默认只有 ✅ 与 ℹ️ 两档，用户可能误以为 ❌ 在警告「匹配很差」。
**应对**：想让三档配色真正用起来，需把「相似度阈值」**和**「最小置信度」一起下调
（只降后者无效，因为候选在更早一步已被丢弃）。
复核时始终以面板显示的百分比数值为准。

### 顶点色复制

#### 7. 目标物体带修改器时，颜色索引会错位

**限制**：取色的顶点坐标取自**求值后网格**（含修改器结果），
但颜色**写入的是原始网格**的颜色层
（`core/vertex_color_ops.py: copy_vertex_colors_between_objects`：
`target_mesh = target_obj.data`，坐标来自 `target_mesh_eval`）。
当修改器改变顶点数或顺序时，两者的顶点**不再一一对应**。
**影响**：目标物体上有细分（Subdivision）、镜像（Mirror）、布尔（Boolean）、
实体化、简化（Decimate）等会改变拓扑的修改器时，
写入的颜色可能落到错误的顶点上，表现为花斑、错位或只写进去一部分，
**且不报任何错**。源物体一侧不存在这个问题——源的颜色和坐标同取自求值网格，
索引天然对齐。**应对**：**复制前先应用（Apply）目标物体的修改器**；
或临时关掉再复制、复制后开回来。修改器只影响显示、不改变拓扑
（如置换 / Wave）时不受影响。

#### 8. 最近顶点取色默认没有距离上限，超出源范围的顶点会被「拉色」；可用「取色距离上限」缓解

**限制**：KDTree 查询只取最近点，**默认不判断该点有多远**
（`_copy_colors_to_attribute_kdtree`；原生路径同样不判断，
见 `native/vct_native.cpp: vct_kdtree_query_colors`）。源顶点若无颜色记录，填白色。
**影响**：目标模型比源模型大、或两者位置有偏移时，
超出源包围范围的顶点会取到源边缘顶点的颜色，形成**向外扩散的色带**，
而不是保持原色。
**缓解手段**：工具提供 **「优化处理 → 取色距离上限」**（`pick_distance_percent`，
**默认 0 = 完全关闭**）：取色距离超过「源包围盒对角线 × 本值」的目标顶点
**不写入颜色**（保留原色），超范围一眼可见。按对角线百分比归一，换模型尺度依然有效。
- **守护**：源退化（单顶点 / 顶点全重合，对角线 ≈ 0）时自动不启用，
  宁可不拦也不把模型涂空白；二次搜索半径同样被上限夹住，兜底不会架空上限。
- **代价**：开启后**自动改用 Python 取色路径**（原生内核尚未实现该约束），
  大模型变慢，见 9.1 的路径表。
- **取值参考**：10~20% 通常容纳 LOD 差异；两模型几乎重合时 1~5% 足够；
  调太小会漏掉本该上色的顶点（色块缺口），调太大等于没开。
- **默认关闭 = 行为与本功能上线前逐字一致**，不改变任何现有用户的结果。

#### 9.1 薄壁模型可能跨面取色；可用「法线夹角阈值」缓解

**限制**：最近邻只看**距离**，不看**朝向**。对薄壁几何体（墙、树叶、旗帜、布料、纸片、
单面片建模的护甲 / 门板 / 卡牌等——**LOD 游戏资产里这类薄壳模型非常常见**），
壁两侧的顶点距离几乎相等，最近点可能落到**另一面**上，
表现为「墙背面染上了墙正面的颜色」。**没有任何报错或警告**，工具会正常返回成功。
实测：厚度 0.02 的薄墙，目标点落在厚度中线时，前后两面顶点的距离平方仅差约 2e-4，
归属完全由浮点噪声决定。
**缓解手段**：工具提供 **「优化处理 → 法线夹角阈值」**（默认 75°），开启后若最近点与
目标点的法线夹角超过阈值，会在附近改找**朝向一致**的顶点，从而避免跨面取色。

> **⚠ 关键：两条约束任一启用都会自动改用 Python 取色路径，不再走原生加速。**
> 原因是原生 C++ 内核的最近点查询只按距离、不看法线不限距，
> **法线约束与取色距离上限均未实现**（见上方路径表）。
> 若不禁用原生加速就会「界面显示已启用、实际毫无作用」
> ——这正是本工具在 v1.1.0 修掉的另一类静默失效问题。

| 法线夹角阈值 | 取色距离上限 | 取色路径 | 说明 |
|---|---|---|---|
| `0` | `0` | **原生 C++ 内核** | 默认，最快；不防跨面、不防拉色 |
| `>0` | 任意 | **Python** | 防跨面；大模型明显变慢 |
| 任意 | `>0` | **Python** | 防拉色；大模型明显变慢 |

两条约束是「或」关系：**任一启用即绕过原生**，走 Python 路径；
全部设为 0 可恢复原生加速。

- **设为 0 即完全关闭**，退回纯距离最近，便于遇到「某些模型取色反而变差」时快速回退对比。
  **取舍是零和的**：不在意串面就留 `0`（享受原生加速），遇到串面才开（接受变慢）。
- **调不奏效时会退回纯距离最近**（附近没有朝向一致的候选，例如单面片、法线未烘焙、
  稀疏网格）。这是刻意兜底——优先保证「不丢色块」，所以串面重新出现属**预期，不是 bug**。
- **不是万能解**：只解决「跨面」，不解决第 9 条的「色块感 / 噪点」（那是顶点分布差异导致的）。
- **大模型的实际代价（本机 20 万顶点实测）**：Python 路径开启法线约束比关闭慢约 **5 倍**
  （0.11s → 0.67s）。⚠ 该数字是**最坏情况**——测试机没有 numpy，法线变换走的是逐顶点
  Python 循环；Blender 自带 numpy，走向量化路径后这部分约 380ms → 4ms
  （**~95x，float64 实测**），预计真实环境开销会小得多。**请以自己环境实测为准**。
  > 精度说明：法线变换刻意使用 **float64** 而非 float32。法线归一化后直接参与
  > 「夹角 > 阈值」判定，float32 只有约 7 位有效数字，在阈值边界足以让判定翻转，
  > 进而**把颜色落到错误的顶点**上。

#### 12. 缓存不会因为源颜色或源物体变换变化而失效，可能拿到旧数据

**限制**：源数据缓存（`core/cache.py`）按「对象地址 + 层名 + **顶点数**」做键
（`_make_cache_key`，返回 `(as_pointer(), layer_name, vertex_count)`），
上限为**条目数 50 条**与**内存 256 MB 双维度**（`_max_cache_size` /
`CACHE_MEMORY_BUDGET_BYTES`，用户可在面板调整）；单条目估算字节数超过总预算时**不缓存**。
**没有任何网格数据变更的失效钩子**，只在打开新 `.blend` 时清空。
由于键里含顶点数，失效边界很明确：**改拓扑（增删顶点）→ 键变化 → 自动失效（miss）**；
**只改颜色（顶点数不变）→ 键不变 → 命中旧缓存**；
**移动 / 旋转 / 缩放源物体 → 键不变 → 命中旧缓存**——键里**不含 `matrix_world`**，
而缓存内容里的顶点坐标是**世界坐标**（`matrix_world @ vert.co`），
因此这一项会拿到**移动前的位置**去取色。
**影响**：给同一个源物体重新上色后再次复制（顶点数未变）**会拿到上一次的旧颜色**，
无任何提示；移动源物体后再次复制则**静默错位**（用旧位置去源网格里找最近点）
——移动比改色更隐蔽，它错的是位置对应的颜色，不只是「颜色旧了」。
**应对**：改过源物体的**颜色或变换**后，点「优化处理面板 → **清空缓存**」
（v1.1.0 新增的按钮），或关闭「缓存」再复制一次。改拓扑则不必担心。

> 把 `matrix_world` 纳入缓存键是更彻底的方案，但会引入浮点比较与哈希稳定性问题，
> **尚未实现**，已列入 README「未来迭代路径」。

| 23 | 匹配 / 统计**递归含所有层级子集合**（v1.1.0 起改为与大纲可见范围一致，见 CHANGELOG 行为变更）；数据层遍历**不感知视图层排除**——被排除的子集合仍会被纳入；跨链接库**同名物体按名去重会丢弃第二个** | 无法再用「子集合」做范围隔离：需要隔离请改用**多个互不嵌套的顶层集合**分批；不想处理某批物体请把它移出组集合（而非仅排除视图层） |
| 24 | 只处理 `type == 'MESH'` 的物体（非网格静默跳过）；填充操作会整体切到物体模式再切回 | 曲线 / 点云 / 实例不会被处理。编辑模式下的填充是「只填选中顶点」，**若没选中任何顶点则会填满整个网格**。先转网格；编辑模式填充前先明确选中范围 |

## 三、测试与 CI 覆盖范围

`.github/workflows/test.yml` 共 2 个 Job：① **快速检查**（ubuntu + **必须装 numpy**）
跑 `scripts/run_ci_checks.py` 的 9 项——语法检查、P0 断言可证伪性、聚类等价性（900 场景）、
匹配等价性（35 场景）、法线约束、取色距离上限、判定逻辑验收、真 numpy 通道；
② **Blender 无头测试**（ubuntu + 官方 Blender 3.6 LTS）跑 `tests/` 下 4 个文件，
经 `scripts/run_blender_tests.py` 强制转成退出码。
Job 1 **必须装 numpy**：不装则跑的是「`list[Vector]` 回退」，
而真实环境（Blender 自带 numpy）的主路径一行都不会被执行
——**这正是上一轮假绿的成因**。无 numpy 时**判为失败**而非静默放过。

**尚未覆盖的场景**（属于「已知可能出问题但未被验证」，使用时请留意并做好备份）：

- **目标**物体（而非源物体）带拓扑修改器时的复制正确性——现有测试只覆盖了**源**物体
  带细分的情况（见第 7 条）；以及**源物体被移动 / 旋转 / 缩放后缓存是否返回旧位置**
  （见第 12 条）。
- 旋转 / 镜像模型的匹配与取色；浮点与字节颜色属性的交叉复制；带修改器的物体参与匹配时
  `vertex_count` 取修改器前值是否造成预期外的扣分。
- 「手动复制」在大模型下的实际阻塞时长（该路径无进度条、无法取消，见第 16 条）。
- **`poll()` 的真实重绘时机与面板视觉呈现**、`prop_search` 写入集合的实际时机。
  无头测试只覆盖数据层逻辑，UI 呈现仍需手工验证
  （`tests/` 4 个套件已于 Blender 3.4.1 实机跑通，CI 在 3.6.14 复验）。
- macOS / Linux 与 **Blender 4.x**：CI 固定 ubuntu + 3.6 LTS 单一组合，
  `test_native_equivalence.py` 在原生库缺失时**整体跳过**，
  跨平台产物需本地 `python native/build.py` 验证。
- **UI 交互与性能回归**：面板交互、进度条、撤销等仍靠手工验证；
  `tests/benchmark_core.py` 的加速比断言不在 CI 内。
